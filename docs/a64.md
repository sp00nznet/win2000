# Windows 2000 on 64-bit hosts: x86-64 and arm64

Goal: Windows 2000's own userland (cmd, winmine, explorer ...) running as a
native 64-bit process, on x86-64 Linux first and then on arm64 (a Raspberry
Pi, an Apple silicon Mac, Android), with no emulator. Until now the Linux
build was an i386 ELF (`gcc -m32`, docs/linux.md), where a guest address is a
host address.

## How: the guest's 4 GB at one base

The lifted C was always written against `ADDR(va)` (pcrecomp
`recomp_types.h`): every guest load and store is `MEM32(x)` =
`*(uint32_t*)ADDR(x)`, every `rep movs` is `recomp_rep_movs(edi, esi ...)`,
every x87 memory operand `*(double*)ADDR(...)`. Flat (`RECOMP_FLAT_MEMORY`),
`ADDR(va)` is `va`; built with `RECOMP_MEM_BASE=B` it is `B + va`, a constant
add. So **the lifted C needs no re-lift**: the same `src/gen/*` files compile
for x86-64 and arm64 unchanged. Indirect calls go through the dispatch table
(guest address -> host function pointer), which is pointer-size agnostic.

`linux_build.sh` takes `ARCH=x86_64` (gcc -m64) or `ARCH=aarch64`
(aarch64-linux-gnu-gcc, a cross build) and builds `NAME-linux-x64` /
`NAME-linux-a64` with `RECOMP_MEM_BASE=0x2000000000` (128 GB: below the
512 GB an arm64 kernel with 39-bit addresses gives a process, and clear of
x86-64's and arm64's program, heap and library areas; `MEM_BASE=` overrides).
The i386 build is unchanged (`ARCH` defaults to i386, same output names).

## Survey: what assumed guest == host

The lifted C: nothing (above). `RECOMP_LOCAL_REGS`, the flags, x87 (doubles,
`fp_ld80`/`fp_st80` in software, no `long double`), SSE (C fallbacks) are all
portable; `__rdtsc` already has a non-x86 fallback; `CPUID` answers nothing
off MSVC (as the i386 Linux build always did).

The host side, pcrecomp `runtime/native32/ntposix.c` (the NT kernel's half)
and `w32kposix.c` (win32k), was written in guest addresses throughout
(`uint32_t` everywhere, `MEM32`), which made the port small:

| Assumption | Where | Based fix |
|---|---|---|
| `(T*)(uintptr_t)va` makes a host pointer of a guest address | 94 sites in ntposix, 44 in w32kposix | `(T*)ADDR(va)` (mechanical) |
| `(uint32_t)(uintptr_t)p` hands a host pointer to the guest | 11 + 20 sites | `GVA(p)`: flat the same number, based `p - base`, and a pointer outside the 4 GB stops the run with its name (`ntp_bad_gva`) |
| a host stack local handed to the guest (an out handle, CREATESTRUCT, WINDOWPOS, NCCALCSIZE rects, PAINTSTRUCT, MINMAXINFO, CBT_CREATEWND, a callback's message, SetWindowLong's STYLESTRUCT, CreateWindowEx's class and window names) | csrss connect, NtQueryInformationFile(AttributeTag), ~14 w32kposix services | `GUEST_LOCAL(T, name, n)` / `GUEST_ARRAY`: carved below the guest's esp for the call (as the NT kernel copies a user-mode callback's arguments onto the user stack), given back at scope end (`__attribute__((cleanup))`); flat builds do the same |
| a host `malloc` buffer handed to the guest | RLE DIB rows (`dib_plain`), the font enumeration buffer (`g_efd`) | guest memory (`ntp_alloc`) |
| process start's current-directory open with host locals | `ntp_boot` | one guest page |
| `mmap(MAP_FIXED_NOREPLACE)` at the guest address, `p == a` | page map | at `ADDR(a)`; nothing is reserved up front: a 4 GB span at the base is free on a 64-bit host |
| the fault handler's `si_addr` is a guest address; `REG_EIP` | `crash` | `si_addr - base`, inside the 4 GB only; `HOST_PC` per arch (EIP, RIP, arm64 `pc`) |
| `#error` unless i386 | ntposix.c | only when flat |
| a launched program is `./NAME-linux` | win2000 `nthost_linux.c` | `NAME-linux` + the build's suffix (a 64-bit shell starts 64-bit runners) |

Checked and fine as they are: TEB/PEB/KUSER_SHARED_DATA are at guest
addresses (`g_fs_base` is a guest address, `fs:[n]` is `MEM32(g_fs_base+n)`);
thread stacks are guest memory (the guest's kernel32 allocates them); host
pthreads carry the machine lock and swap the register file as before; SEH
landing pads are setjmp/longjmp on host frames (`recomp_eh_*`), portable;
csrss is answered inside ntposix (csr32.c is the Windows host's); guest
varargs are formatted by the guest's own msvcrt/ntdll; the shared-memory
surface between explorer and its children (`W2K_SHM`) is host-only, laid out
with fixed-size fields, and both ends are the same build; the X11 frontend is
host-only; no inline asm anywhere in ntposix/w32kposix/w32klayout/nthost_linux.

`-Wall` on x86-64 after the port: no pointer/integer size warnings.

## Host pages bigger than 4 KB

NT commits and protects 4 KB pages. Apple silicon (16 KB), a Raspberry Pi 5's
default kernel (16 KB) and some arm64 servers (64 KB) cannot `mprotect` 4 KB.
ntposix now asks `sysconf(_SC_PAGESIZE)` and, above 4 KB, protects whole host
pages (`host_protect`): one is read/write when any 4 KB page in it is
committed and accessible. Reservations are 64 KB aligned (NT's allocation
granularity), so two never share a host page. A decommit there keeps the
memory (not zeroed). Untested on a real 16 KB host: qemu-aarch64 runs on the
x86 box's 4 KB pages.

## arm64 hardware: none on the network

Looked in `C:/myhome` (the server list) and the netlab notes
(`recomp-netlab/local/machines`, `docs/machines.md`, `docs/builders.md`): the
machines are the Windows test VMs, the Debian test VM (`netlab-linux`,
x86-64), the Proxmox hosts and their containers (x86-64), and the macOS VM
`netlab-mac` (VM 200 on dpiprox), which is **x86_64** (macOS 15 on Proxmox),
not Apple silicon. No Raspberry Pi, arm64 VM or Apple silicon Mac. So arm64
is a cross build (`aarch64-linux-gnu-gcc` on netlab-linux) run under
**qemu-aarch64 user mode as a stand-in for real hardware**: qemu emulates the
*host* CPU (it runs our arm64 ELF on the x86 box); the Windows 2000 code is
still statically recompiled C, never emulated. On a real arm64 Linux box
(Pi 4/5, Graviton, an Ampere VM) the same `NAME-linux-a64` runs directly.

## A Mac (Apple silicon): survey and plan (not built: no Mac with arm64 here)

The based build is the hard part and is done; a Mac host layer is the rest.
What differs from Linux in ntposix / w32kposix / nthost_linux:

| Linux-only | Mac equivalent |
|---|---|
| `MAP_FIXED_NOREPLACE` | none: `mmap` with the address as a hint and no `MAP_FIXED`, then the existing `p == ADDR(a)` check (define `MAP_FIXED_NOREPLACE 0`); or one `mach_vm_allocate` of the whole 4 GB at the base and `MAP_FIXED` inside it, as win32hle's guest_mem.c does |
| `memfd_create` (shared sections) | `shm_open` + `shm_unlink` (an anonymous shared fd), or `mkstemp` + `unlink` |
| `prctl(PR_SET_PDEATHSIG)` (a child dies with the shell) | a pipe the child polls, or `kqueue` `EVFILT_PROC NOTE_EXIT` on the parent |
| `/proc/self/exe` (where the runners are) | `_NSGetExecutablePath` |
| `ucontext` `gregs[]`, `st_mtim` | `uc_mcontext->__ss.__pc`, `st_mtimespec` |
| `PTHREAD_RECURSIVE_MUTEX_INITIALIZER_NP` | `pthread_mutexattr_settype(RECURSIVE)` once |
| 4 KB pages | 16 KB: `host_protect` (above) already handles it |
| X11 window (`W2K_X11`) | XQuartz's libX11 (`/opt/X11`) works as is for a first light; native later: a Cocoa or SDL2 window over the same framebuffer (pcrecomp's win32hle already draws through SDL2 on macOS) |

Base: `0x2000000000` is free on macOS arm64 (programs load at 0x100000000
behind a 4 GB `__PAGEZERO`, dyld's shared cache is at 0x180000000+); W^X
does not matter (nothing is generated at run time). Build: Apple clang,
`-arch arm64`, the same `RECOMP_MEM_BASE`. The farm's `macos` builder
(`builders/macos/setup.sh`) on an Apple silicon Mac would build it; the
existing `netlab-mac` VM is x86_64 and could test the x86-64 Mac build of the
same code (based, 4 KB pages) in the meantime.

Android: the Linux build with the NDK (bionic has `memfd_create` from API 30,
no `pthread` cancellation, no X server: Termux:X11, or an SDL/ANativeWindow
frontend over the framebuffer). Untested.

## Box setup for the arm64 stand-in (removed again afterwards)

```
sudo dpkg --add-architecture arm64 && sudo apt-get update
sudo apt-get install --no-install-recommends gcc-aarch64-linux-gnu libc6-dev-arm64-cross     qemu-user qemu-user-binfmt libx11-dev:arm64     # ~1 GB; binfmt lets explorer exec its arm64 children
ARCH=aarch64 sh linux_build.sh ntwinmine            # NAME-linux-a64
qemu-aarch64 -L /usr/aarch64-linux-gnu ../winmine-linux-a64 --out out/a64 ...
SFX=-a64 LIVEARGS=... sh ../linux_live.sh explorer out/a64live ...   # longer sleeps: qemu is slower
```

At the end the packages were purged and the arm64 architecture removed from
netlab-linux (`apt-get purge --allow-remove-essential` of the `:arm64`
packages only; `dpkg --remove-architecture arm64`); the scratch directories
(`~/a64`, `~/a64w`, `~/a64e`) were deleted. The box has 4.5 GB free; one
set's x86-64 or arm64 objects are ~700 MB, so build one set at a time and
delete `obj-*` after linking.

## Handoff (next)

1. **Real arm64 hardware.** A Raspberry Pi 4 (4 KB pages, 39-bit VA: the
   base 0x2000000000 fits) runs `NAME-linux-a64` as built here; a Pi 5 or
   Asahi Linux (16 KB pages) exercises `host_protect`, untested. On an arm64
   box `ARCH=aarch64` uses its own gcc (no cross toolchain).
2. **The other accessories** on x86-64/arm64 (calc, notepad, sol, freecell,
   mspaint, wordpad): no code differs, only builds and shots to compare
   (`int`/`calc`/`np`/`fc` scripts in docs/linux.md).
3. **Speed.** The lifted C is `-O0` (as everywhere); on 64-bit hosts
   `ADDR` is a constant add, so `-O1` on the lifted C is worth measuring.
4. **macOS** (above): the host-layer table, then XQuartz first light on an
   Apple silicon Mac; the x86_64 `netlab-mac` VM can test the based build
   with 4 KB pages first.
5. **Android**: NDK build + an SDL/ANativeWindow frontend.
